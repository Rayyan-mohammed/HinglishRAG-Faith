## Architecture Decisions

### ADR-001: Same model (Groq llama-3.3-70b-versatile) for both generation and verification
**Decision:** Use one Groq-hosted model for both answering the question and judging claims against evidence, with separate prompts for each role.
**Why:** Free tier, no GPU, one API key to manage, fast enough to run 50-80 questions in minutes.
**Impact:** Open risk — a model may be more likely to rate its own generation style as supported (self-verification bias). Not corrected for; worth checking during error analysis (Week 4) whether missed hallucinations cluster around a particular phrasing style.

### ADR-002: BAAI/bge-m3 as the sole embedding model, run locally
**Decision:** One pretrained multilingual embedding model for all retrieval (question-level and per-claim), no fine-tuning.
**Why:** Handles Hindi-English mixed text out of the box; free; no training budget or GPU in scope.
**Impact:** Retrieval quality is whatever bge-m3 gives on Hinglish — not tunable within the project. A retrieval failure and a verification failure will look identical from the outside unless logged separately.

### ADR-003: Rule-based claim decomposition (sentence boundaries + connector-word list)
**Decision:** Split generated answers into atomic claims with regex sentence splitting plus a fixed connector-word list (aur, lekin, but, however, ...), not a trained parser.
**Why:** Transparent, debuggable, sufficient at this scale; a full parser is unnecessary engineering for a 4-week course project.
**Impact:** Known failure mode — will mis-split some code-mixed sentences. Mitigation is manual review of decomposition output during Week 3 (see B3) and adjusting the connector list, not a general fix.

**Update (Week 4 error analysis, `docs/error_analysis.md`):** Found a second failure mode of the same kind: splitting a compound "context has *only* X and Y" claim on "aur" into "has X" + "has Y" silently drops the exhaustiveness qualifier ("only"), turning one false claim into two individually-true fragments. This directly caused 2 of the verifier's 6 false negatives (Q51). Same category of problem as the "aur"-as-compound-subject limitation above — a rule-based splitter has no way to know a connector is joining two objects of a shared qualifier rather than two independent statements. Not fixed, recorded as a second concrete example of this limitation's cost.

### ADR-004: FAISS flat index (in-memory, local), no vector DB server
**Decision:** `IndexFlatIP` over normalized embeddings, rebuilt from scratch by `scripts/build_index.py`.
**Why:** 3-5 documents means brute-force cosine similarity is instant; a server-backed vector DB would be pure overhead.
**Impact:** Doesn't scale past course-project size — fine here, would need revisiting for more documents.

### ADR-005: Per-claim retrieval, not reuse of the question-level retrieval
**Decision:** Stage 4 re-queries the index with each individual claim rather than reusing the passages retrieved for the original question.
**Why:** The passage that best supports the whole answer isn't always the passage that supports any one claim inside it.
**Impact:** Doubles retrieval calls per question (cheap, local) but adds a second retrieval failure mode to account for during error analysis — a claim can be correct but get flagged wrong because per-claim retrieval missed the right passage.

### ADR-006: Single annotator for the 50-80 question ground-truth set
**Decision:** Partner B hand-labels every generated answer (fully correct / partially hallucinated / fully hallucinated) alone.
**Why:** Team of 2 at course-project scale; coordinating a second labeller for inter-annotator agreement isn't in the 4-week budget.
**Impact:** No inter-annotator agreement number. Disclosed as a limitation in the final report rather than hidden. Consider re-reviewing a random sample of labels a second time before finalizing (see risk table in blueprint Section 17).

### ADR-007: uv + pyproject.toml for dependency management
**Decision:** Project dependencies declared in `pyproject.toml`, resolved and locked with `uv` (`uv.lock`), no `requirements.txt`.
**Why:** Reproducible lockfile, faster installs than pip, single tool for venv + deps + running scripts.
**Impact:** Contributors need `uv` installed. `uv run pytest` doesn't work on this machine due to a Windows Application Control policy blocking `pytest.exe` — use `uv run python -m pytest` instead.

### ADR-008: `config/` package separated from `src/` pipeline code
**Decision:** All settings (model names, paths, API key loading) live in `config/settings.py`, imported by `src/*.py`, not inlined.
**Why:** Keeps model/version choices and paths in one place instead of scattered across pipeline modules.
**Impact:** One extra import line per module; negligible cost for the clarity.

### ADR-009: Fixed scheme list — PM-KISAN, Ayushman Bharat, Post-Matric Scholarship, PM Awas Yojana
**Decision:** These 4 schemes, chosen upfront so Track B could start writing evaluation questions in Week 1 without waiting on Track A's document collection.
**Why:** All well-known, high-traffic .gov.in schemes with clear eligibility/deadline/amount/document facts to ask about; matches the blueprint's example set in Section 12. 4 schemes keeps the 60-question set balanced at 15 questions each.
**Impact:** Track A's Week 1 document collection (A1) should target exactly these 4, using these names, so `eval/questions.csv`'s `scheme` column joins cleanly to `data/schemes/` once built.

### ADR-010: `judge()` split out from `verify_claim()` in `src/verification.py`
**Decision:** The LLM-as-judge prompt call now takes `(claim, evidence_text)` directly, with `verify_claim()` doing retrieval and then calling `judge()`.
**Why:** B1 needs to test the verifier prompt on 5 hand-written claim/evidence pairs before any retrieval index exists. Splitting the functions means that test doesn't need a fake index or fake passages.
**Impact:** None to existing behavior — `verify_claim()`'s output is unchanged, just calls through `judge()` now.

### ADR-011: `data/schemes/` is one structured facts CSV per scheme, fetched live from source, not free-text documents
**Decision:** Replaced the earlier plain-text scheme documents in `data/schemes/` with one CSV per scheme (`PM-KISAN.csv`, `Ayushman Bharat.csv`, `PM Awas Yojana.csv`, `Post-Matric Scholarship.csv`; columns: `category`, `fact`, `source_url`). Each row is one atomic fact extracted directly from an official `.gov.in` source. These files are generated by `scripts/fetch_scheme_data.py`, which fetches multiple real source documents per scheme over HTTP (operational guideline PDFs, FAQ PDFs/pages, benefit-summary pages) and parses each with one of five heuristics — `faq` (numbered Q&A), `sections` (lettered/roman-numeral clause headers), `clauses` (decimal-numbered clauses like `5.1.6`), `numbered` (plain numbered statements), `bullets` (one fact per line) — rather than being hand-copied. Re-running the script re-derives the dataset from the current live sources. Final counts: PM-KISAN 43 rows (Operational Guidelines + Revised FAQ + Additional FAQ), Ayushman Bharat 37 (FAQ + Benefits page), PM Awas Yojana 58 (FAQ + PMAY-U 2.0 Operational Guidelines, capped at 40 clauses), Post-Matric Scholarship 34 (national guidelines PDF + Maharashtra state page) — 172 facts total. `src/retrieval.py`'s `build_index()` reads every `*.csv` in `data/schemes/`, using each file's name as `passage["source"]`, and embeds each row's `fact` as its own passage. The old `chunk_text()` word-splitting step was removed since rows are already short enough to embed without chunking.
**Why:** Partner A wanted a structured, auditable, per-scheme dataset (one row per fact, with its source URL, reproducible by re-fetching) rather than prose documents or a single merged file, so every fact fed to the pipeline can be traced back to its official source and regenerated on demand.
**Impact:** Retrieval quality trade-off, flagged before implementing: bge-m3 embeddings of short atomic facts about the same scheme are more similar to each other than embeddings of full prose paragraphs, so at low `top_k` (e.g. `verify_claim()`'s default of 2) the single most relevant fact can occasionally rank below other facts about the same scheme. At the project's default `TOP_K=4` this wasn't observed to be a problem in spot checks, but it's worth watching during Week 3 error analysis — if per-claim verification (`top_k=2`) starts missing evidence that's clearly present in the dataset, raising that default is the first thing to try. A second risk: the fetch script's HTML/PDF parsing is heuristic (marker-text slicing, regex section/question splitting) and can silently miss or garble a section if a source page's structure changes — anyone re-running it should spot-check row counts and a few sample rows per scheme before trusting a refresh.

### ADR-012: Ground-truth labels for `eval/labels.csv` are an AI-drafted first pass, not yet human-reviewed
**Decision:** All 60 rows in `eval/labels.csv` were labelled by reading each generated answer in `results/generated_answers.csv` against the source facts in `data/schemes/*.csv` and assigning fully_correct / partially_hallucinated / fully_hallucinated with a note citing the specific supporting or contradicting fact. This was done by Claude, not by Rayyan. Every row has `reviewed_by_human=FALSE`.
**Why:** The blueprint (ADR-006) explicitly frames ground-truth labelling as done by the human author alone — the whole point of an independent ground truth is that it isn't produced by the same kind of system (an LLM) as the verifier being evaluated against it. Doing the full manual pass would have taken Rayyan significant time this session; drafting it and flagging it clearly for review was the agreed tradeoff (chosen explicitly over two alternatives: leaving it undone, or generating it with no disclosure).
**Impact:** Precision/recall computed against this file (B3/B4) should be treated as provisional until a human reviewer spot-checks it and flips rows to `reviewed_by_human=TRUE` (or corrects the label). Any report or presentation using these numbers must disclose that the ground truth started as an AI-assisted first pass — presenting it as pure manual annotation would misrepresent the evaluation methodology. Distribution of the draft: 42 fully_correct, 12 partially_hallucinated, 6 fully_hallucinated.

### ADR-013: `verifier_results.csv` verifies the existing plain answers directly, doesn't re-generate a separate "verified" pipeline
**Decision:** `scripts/verify_answers.py` (B3) decomposes and verifies the 60 already-generated `pipeline == "plain"` answers in `results/generated_answers.csv` in place. It does not call the generator again, and `generated_answers.csv` never gets `pipeline == "verified"` rows — `results/README.md` originally planned for those, and has been corrected to match this.
**Why:** The blueprint's own architecture (Section 10, Stage 6) has verification aggregate per-claim verdicts back onto the *same* generated answer for display — it's a post-hoc annotation layer, not a second generation pass with a different prompt. Re-generating a second time would also introduce a confound: any difference between "plain" and "verified" answer text could be explained by generation randomness (`temperature=0.4`) rather than by verification actually being on or off, which would make the Section 13.1 plain-vs-verified comparison unreliable. Using the same 60 answers for both conditions means the only thing that differs between "plain" and "verified" is whether the verification layer's tags are shown — exactly what Section 13.1 intends to compare.
**Impact:** `generated_answers.csv` stays exactly as A2 produced it. `results/verifier_results.csv` is the only new file, keyed by `question_id` + `claim`, and joins back to `generated_answers.csv` via `question_id`. Anyone computing the plain-vs-verified comparison should treat "plain" as `generated_answers.csv`'s raw text and "verified" as that same text with `verifier_results.csv`'s per-claim tags applied — not as two different answer sets.

### ADR-014: `eval/claim_ground_truth.csv` — a second, claim-level ground truth pass, derived from `eval/labels.csv`
**Decision:** The blueprint's Section 14 protocol defines ground truth at answer level (fully_correct / partially_hallucinated / fully_hallucinated — what `eval/labels.csv` already has), but Section 13.2's precision/recall metrics are defined at claim level ("of all the claims... identified as hallucinated..."). Answer-level labels can't compute that directly, so `scripts/build_claim_ground_truth.py` re-checked every one of the 60 claims decomposed from the 18 non-fully_correct answers individually against the source facts (the 42 fully_correct answers' 152 claims are ground-truth non-hallucinated by construction — the whole answer was already confirmed correct). Output: `eval/claim_ground_truth.csv`, one row per claim in `results/verifier_results.csv` (row-aligned), with a `true_hallucinated` bool.
**Why:** This is the only way to compute the metrics the blueprint actually specifies, rather than only the answer-level catch rate. It surfaced something the answer-level pass missed: of the 18 flagged answers, only 11 actually contain an individually-false claim. The other 7 (Q14, Q16, Q26, Q40, Q45, Q52, Q58) were flagged for *relevance or completeness* problems — right facts, wrong scheme cited alongside them, or an omitted general criterion — where every individual decomposed claim, checked on its own against *some* fact in the dataset, is technically true. A claim-level supported/contradicted/unverifiable check cannot catch that class of problem by construction, no matter how good the verifier is — the earlier ADR-005 discussion of per-claim retrieval and P-004's cross-scheme contamination note both undersold this until it was traced claim-by-claim. Two labels also got revised on the closer look: Q26 was originally called partially_hallucinated but its actual phrasing ("context has no info saying the amount varies by state") is an honestly-hedged true statement, not an overclaim — same pattern as the genuinely fully_correct answers (Q6, Q7, Q20...); Q40's Rs 400-1350 figure is a real fact in the dataset (Maharashtra-specific), just inconsistent with the national Group I-IV figure given in Q38, not unsupported.
**Impact:** This file, not `eval/labels.csv` directly, is what `scripts/compute_metrics.py` uses for claim-level precision/recall. Same disclosure as ADR-012 applies — AI-derived, not yet reviewed by a human — and it inherits `eval/labels.csv`'s provisional status plus this file's own judgment calls on top. The 7-answer relevance/completeness gap is itself a finding worth keeping in the final report, not just a methodology footnote: it's a concrete answer to "what kind of hallucination does this verification approach structurally miss."

### P-001: Groq free-tier daily token limit hit mid-generation-run
**Week:** 2
**Problem:** Running `scripts/generate_answers.py` (A2) against all 60 eval questions hit Groq's free/on-demand tier limit of 100,000 tokens per day (TPD) partway through — the run stopped at question 56/60 with a `RateLimitError`, then again at 57/60 and 59/60 on subsequent attempts as newly-freed tokens got used up by the next call. This is a rolling-window daily quota, not a short-term rate limit, so retrying every 30s for 6 minutes didn't help — but the error message's "try again in Nm" countdown was accurate: it's a rolling 24h window that frees up tokens gradually, so waiting the full countdown (each attempt needed anywhere from ~5 to ~25 minutes) did eventually work.
**Fix:** Made `scripts/generate_answers.py` resumable — it now reads any existing `results/generated_answers.csv`, skips `question_id`s already present, and only generates the missing ones. This let completed answers be committed as progress instead of being discarded or re-generated (re-spending tokens) on every retry, and meant each retry only needed enough freed-up quota for the handful of questions still missing, not the full batch. All 60 answers were completed this way across roughly three rate-limit windows.
**Lesson:** For any future full-batch run against the Groq free tier (e.g. B3's per-claim verification pass in Week 3, which will multiply the number of calls by the average claims-per-answer), budget for hitting this same 100k-tokens/day ceiling more than once and design the driving script to be resumable from the start, not after the first failure. Trust the error message's countdown — it's a real rolling-window estimate, not a fixed daily reset.

### P-002: `src/decomposition.py` mis-splits on abbreviation periods and "aur"-joined compound subjects
**Week:** 3
**Problem:** While proactively testing `decompose()` against all 60 real generated answers (in support of B3, which finalizes decomposition against real output), 2 of 60 answers produced very short, meaningless claim fragments — `'EWS'` and `'Rs'` on their own. Root causes: (1) `split_sentences()`'s regex (`(?<=[.!?])\s+`) treats the period in an abbreviation like "Rs." as a sentence boundary whenever it's followed by whitespace, so "Rs. 3.00 lakhs" gets split into "Rs" + "3.00 lakhs"; (2) `split_on_connectors()` splits on every occurrence of "aur", including when it joins a compound subject rather than two independent claims (e.g. "EWS aur LIG category ke liye income criteria hai" → "EWS" + "LIG category ke liye income criteria hai").
**Fix:** Split the two cases once it was clear they needed different treatment. The abbreviation-period case (1) is a clean, unambiguous mechanical bug with no existing test asserting the broken behavior, so it's fixed directly in `split_sentences()`: a negative lookbehind (`(?<!Rs\.)`) keeps "Rs." from being read as a sentence boundary. Verified against all 60 real answers — the lone `'Rs'` fragments are gone (claim count dropped from 225 to 212 as the falsely-split pieces re-merged), with a new regression test (`test_rs_abbreviation_does_not_split_sentence`) added to `tests/test_decomposition.py`. The "aur"-as-compound-subject case (2) was deliberately left alone — `tests/test_decomposition.py::test_known_limitation_noun_phrase_connector` already locks in and documents this exact behavior as an accepted limitation per ADR-003 ("adjusting the connector list... not a general fix"), owned by B3. Overriding it with a generic heuristic (e.g. merging short fragments) would have broken that test and pre-empted Track B's manual-review judgment call on more data than the 2 cases found here.
**Lesson:** When a "known limitation" already has a test locking in its current behavior with a docstring explaining why, that's a signal the team already decided not to fix it generically — check for that before changing shared code, even when a fix looks easy. The abbreviation case had no such guard, which is what made it safe to fix directly instead of only flagging it.

### P-003: Groq removed `llama-3.3-70b-versatile` entirely — GENERATOR_MODEL/VERIFIER_MODEL were broken for the whole team
**Week:** 3
**Problem:** While testing the Week 3 demo skeleton, every Groq call started failing with `NotFoundError: Error code: 404 - The model 'llama-3.3-70b-versatile' does not exist or you do not have access to it`, even though this exact model had generated all 60 Week 2 answers successfully earlier. Calling `client.models.list()` confirmed it: the model is gone from Groq's catalog entirely, along with every other Llama chat model — the current active list is `allam-2-7b`, `groq/compound`, `groq/compound-mini`, `openai/gpt-oss-120b`, `openai/gpt-oss-20b`, `openai/gpt-oss-safeguard-20b`, `qwen/qwen3.6-27b`, plus audio-only and guard-only models. This broke `GENERATOR_MODEL` and `VERIFIER_MODEL` in `config/settings.py` (ADR-001) for every team member, not just one script.
**Fix:** Tested the two most plausible replacements on both the generation prompt and the verifier's JSON-output prompt: `qwen/qwen3.6-27b` is a reasoning model that prepends a huge `<think>...</think>` block to every response (including the verifier's supposed-to-be-JSON-only output) — unusable without adding a strip step, and would burn through the daily token budget from P-001 far faster given how verbose the reasoning traces are. `openai/gpt-oss-120b` and `openai/gpt-oss-20b` both gave clean, correct Hinglish answers and clean, strict JSON verdicts (`{"verdict": "SUPPORTED", "confidence": 0.99}`) with no extra wrapping. Set both `GENERATOR_MODEL` and `VERIFIER_MODEL` to `openai/gpt-oss-120b`, keeping ADR-001's "same model for both roles" decision intact.
**Lesson:** Don't assume a model name that worked earlier in the same project still works later — Groq's free-tier catalog can change without warning, and unlike a rate limit this fails every single call with no retry that helps. If Groq calls start failing with a 404 `model_not_found` (not a 429), check `client.models.list()` before assuming it's a config or code bug. The already-generated `results/generated_answers.csv` content from Week 2 is unaffected (it's just text, sourced from the old model at the time), but anyone re-running generation or starting verification needs this model swap.

### P-004: Cross-scheme retrieval contamination found while drafting ground-truth labels (ADR-012)
**Week:** 2
**Problem:** Manually checking all 60 generated answers against `data/schemes/*.csv` while drafting `eval/labels.csv` turned up something worse than the same-scheme fact-ranking risk ADR-011 already flagged: several answers pull facts from a *different scheme entirely*. Q14 (a PM-KISAN question) cites a PM Awas Yojana fact as supporting evidence. Q30 (Ayushman Bharat) lists "Driving Licence, Voters' ID Card, NREGA Job Card" as required documents — those are PM-KISAN's alternate-ID list for Assam/Meghalaya/J&K, not anything in Ayushman Bharat's facts. Q45 (Post-Matric Scholarship documents) answers with document lists for all 3 other schemes instead of the one asked about. Q52 (PM Awas Yojana) cites Ayushman Bharat's status-check URL. Q58 (PM Awas Yojana income proof) answers entirely with Post-Matric Scholarship's income-certificate rule — the whole answer is about the wrong scheme. That's 5 of 60 questions (~8%) with retrieval pulling from the wrong scheme, not just the wrong fact within the right scheme.
**Fix:** Not fixed — this is a finding for Week 3 error analysis and B3 (verifier wiring), not something patched here. Recorded so it isn't rediscovered from scratch. Two candidate causes worth checking when B3 wires up per-claim retrieval: (1) `TOP_K=4` may be too high for a 172-passage index this small, pulling in genuinely lower-relevance passages from other schemes when nothing better matches within the right one; (2) some questions (e.g. "kaunse documents chahiye", "kya X zaroori hai") are generic enough in phrasing that their bge-m3 embedding doesn't strongly anchor to one scheme, especially when a similar concept (documents, eligibility, ID proof) exists across all 4 schemes' facts.
**Lesson:** ADR-011 anticipated same-scheme fact-ranking noise from embedding short atomic facts; it didn't anticipate the retriever crossing scheme boundaries entirely. This is a genuine retrieval-quality problem, not just a decomposition or verification one — worth checking whether restricting retrieval to the question's target scheme (the `scheme` column already exists in `eval/questions.csv`) is worth doing for evaluation purposes, versus leaving it fully open-index the way a real user's query would face it.

**Update (index now built, live retrieval confirmed):** Once `scripts/build_index.py` finally ran, `retrieve()` was smoke-tested directly against the real 172-passage index with 4 hand-written claims. It reproduces this exact problem live: for the claim "PM-KISAN mein har saal 6000 rupees milte hain," at `top_k=3` the #1 result (score 0.620) is a PM-KISAN passage but the wrong one (exclusion criteria, not the amount fact), and #2/#3 (scores 0.527, 0.523 — close behind #1) are from Post-Matric Scholarship and Ayushman Bharat entirely. At `verify_claim()`'s default `top_k=2`, this claim would get zero correct evidence. The other 3 test claims (Ayushman Bharat, Post-Matric Scholarship, PM Awas Yojana amount facts) retrieved correctly-scoped, reasonably on-point evidence. So this isn't uniform breakage — it's inconsistent, and worse for claims whose phrasing is generic/short relative to the specific fact needed.

### P-005: `scripts/build_index.py` segfaulted repeatedly on low free memory; Groq's short-term TPM limit also isn't caught
**Week:** 2-3
**Problem:** Two separate blockers surfaced getting the index built and the verifier run end-to-end. (1) `embedder.encode()` inside `build_index()` segfaulted (native crash, exit 139) every time free system RAM was below ~4GB — reproduced at 2.4GB, 3.4GB, and 3.8GB free, each time crashing either during the model weight download (`hf-xet`'s Rust backend, `memory allocation of ~67MB failed`) or during the forward pass itself. It only succeeded once free RAM reached ~4.8GB. (2) Once the index existed and `scripts/verify_answers.py` (B3) started making real verification calls, it crashed after 38/212 claims with `groq.RateLimitError: ... tokens per minute (TPM): Limit 8000 ... Please try again in 90ms` — a short burst limit, distinct from P-001's rolling daily quota, that the script had no retry handling for at all.
**Fix:** (1) No code fix possible for the memory issue — it's a host resource ceiling, not a bug. Setting `HF_HUB_DISABLE_XET=1` (forces the plain HTTP downloader instead of the memory-hungry Xet backend) removed one failure mode but didn't fix the encode-time segfault; that only went away with more free RAM. Anyone re-running `build_index.py` on a memory-constrained machine should close other applications first and expect to need roughly 4-5GB free. (2) Added retry-with-exponential-backoff (`time.sleep(2**attempt)`, up to 5 attempts) around the Groq call inside `judge()` in `src/verification.py`, scoped specifically to `groq.RateLimitError`. Re-running `verify_answers.py` (already resumable per its design, skips claims already in `verifier_results.csv`) completed the remaining 174 claims without further manual intervention.
**Lesson:** Two different things both surface as "the run stopped" but need opposite handling: P-001's daily-quota limit needs waiting out (retrying immediately doesn't help, the countdown does), while this TPM burst limit needs a short retry-with-backoff (immediate retry after ~seconds works fine). Check the error message's specific limit type (`tokens per minute` vs a daily/`TPD` reference) before choosing a response. Also: a script crashing partway through a long paid-API run is the normal case to design for, not the exception — every long-running script in this project (`generate_answers.py`, `verify_answers.py`) needed resumability added, not as an afterthought but because it kept actually being needed.

### P-006: Low precision (0.21) traced to two distinct causes, not one — wrong-scheme retrieval and a meta-claim blind spot
**Week:** 3
**Problem:** `scripts/compute_metrics.py`'s first run showed precision of only 0.21 on flagged claims (66 false positives out of 84 flagged) despite a healthy 0.75 recall — the verifier over-flags heavily. Checked whether P-004/P-005's cross-scheme retrieval problem explained it: joined `verifier_results.csv`'s `evidence_source` against each question's true `scheme` (from `eval/questions.csv`) and found 60 of 212 claims (28%) got evidence from the wrong scheme, and of the 66 false positives, exactly 33 (50%) had wrong-scheme evidence. So only half the story. Manually read the other 33 false positives (correct-scheme evidence, still flagged) and found a second, independent pattern: claims that describe the *absence* of information ("context mein X ka ullekh nahi hai," "koi jankari nahi hai," "hum keh nahi sakte") get marked UNVERIFIABLE or even CONTRADICTED by the LLM-judge far more often than not, even when that absence is exactly what the source shows — e.g. Q6's "context mein naye kisan registration ke liye last date ka ullekh nahi hai" is a true statement (no such deadline exists in the PM-KISAN facts) but was still flagged UNVERIFIABLE.
**Fix:** Not fixed — this is the core finding for Week 4 error analysis (B4), not a patch. Recorded with the exact split (50% wrong-scheme evidence, 50% correct-evidence-but-still-flagged) so error analysis starts from a real number instead of a guess. The wrong-scheme half is the same root cause as P-004: generic, low-vocabulary meta-claims ("koi jankari nahi hai") don't carry enough scheme-specific signal for bge-m3 to anchor retrieval to the right scheme, so `top_k=2` per-claim retrieval for these often pulls from elsewhere entirely — most visible in Q17, Q21, Q29, Q36, Q37's evidence sources, none of which match the question's actual scheme.
**Lesson:** The verifier prompt (`VERDICT_PROMPT` in `src/verification.py`) asks the judge to decide SUPPORTED/CONTRADICTED/UNVERIFIABLE for a claim against evidence, but was never designed to handle a claim that is itself a statement *about the evidence's completeness* — there's no instruction telling the judge what to do when the claim says "the evidence doesn't cover this." Two independent fixes are now candidates for Week 4, not yet chosen between: (a) route claims matching an "absence" pattern (a short list of Hinglish/English negation phrases) to a different verification strategy, or exclude them from decomposition entirely since they're meta-commentary rather than checkable facts; (b) add a scheme filter to per-claim retrieval using `eval/questions.csv`'s known `scheme` column, which would directly fix the wrong-scheme half but only works for evaluation (a real deployed system wouldn't know the "correct" scheme in advance).

**Correction (found reviewing A's Week 4 work, after this entry was written):** The "50% correct-evidence-but-still-flagged = absence-claim mishandling" claim above was an overgeneralization — it was based on eyeballing 6-7 examples (Q6, Q17, Q21, Q22, Q29, Q36, Q37) and assumed without checking that the pattern held for the rest. Systematically re-checked all 33 correct-scheme false positives against a list of absence-phrase markers: only **7 of 33** matched. Filed the other 26 under "decomposition producing fragments that aren't real claims" — which turned out to be the same mistake at one level down: a keyword-filtered bucket treated as one cause without reading every entry.

**Second correction (reading all 26 individually, not just filtering them out by keyword):** Only about half of those 26 are genuinely decomposition damage. The rest are complete, accurate, correctly-scoped claims that still got a wrong verdict for no identifiable structural reason — a worse finding than "the input was bad," since it means the verifier/retrieval combination fails sometimes on good input with nothing else to blame. Concrete example: Q42's claim "Agar aap SC category se hain toh aapko caste certificate ki copy bhi lagani hogi" — complete sentence, factually correct (matches the source's application document list exactly), evidence correctly scoped to Post-Matric Scholarship — still came back **CONTRADICTED at 0.92 confidence**. The corrected breakdown of the 33 correct-scheme false positives, read claim by claim:

- **13: genuine decomposition damage** — bare fragments with no predicate (`"EWS"`, `"Assam, Meghalaya"`), a dangling incomplete conditional (Q47's "agar aapke paas pucca ghar hai" cut off before its consequence clause), and list items that lost their shared antecedent when a compound sentence got split on "aur" (4 of Q38's "day scholars" figures, split off from the "Group N ke liye" reference that names which group they belong to — the "hostellers" halves of the same pairs kept their group reference and verified fine). Also includes Q25's "poora kharcha cover hota hai" claim, which is the *same* dropped-qualifier bug already documented for Q51 (ADR-003) — decomposition split it off from its own "lekin sirf 5 lakh tak" cap.
- **12: unexplained retrieval-or-judge failures on well-formed, accurate, correctly-scoped claims** — Q42's caste-certificate claim above, 5 of Q38's "Group N ke liye 1200/820/570/380 rupees hostellers" figures (each a complete, specific, true claim naming its own group — not missing anything), Q14's true cross-scheme content, Q54's subsidy-varies-by-category claim, others in this shape. No decomposition damage, no scheme mismatch, no absence pattern — the claim was simply judged wrong.
- **7: true absence-claim mishandling** (unchanged from the first correction).
- **1: confirmed data staleness (P-007)** — Q9's "Total 6000 rupees... 2000 rupees" claim, CONTRADICTED 0.95. This verifier run used an index built *before* A fixed the corrupted `Rs.60001`/`Rs.20001` rupee amounts in `PM-KISAN.csv` — the judge correctly flagged a true claim against evidence that was, at the time, actually wrong. Not re-measured after the fix.

13+12+7+1 = 33, plus the 33 wrong-scheme cases = 66. The 12 "unexplained" cases are the most concerning of the four, precisely because there's no structural fix to point at — a data logging gap made them harder to diagnose than they should have been: `verifier_results.csv`'s `evidence_source` column only records the top-ranked retrieved passage, not the full evidence text actually sent to `judge()`, so it's not possible after the fact to tell whether the judge saw the right passage and misjudged it, or saw a subtly-wrong passage despite the scheme label matching. Worth logging the full evidence text in any future run.

### P-007: `data/schemes/PM-KISAN.csv` had corrupted rupee amounts from a malformed source PDF
**Week:** 4
**Problem:** Manually testing the finished demo (A4) live, asking a plain PM-KISAN amount question returned "Rs. 60,001 per year... Rs. 20,001 per installment" — and the verifier marked it SUPPORTED at 0.98 confidence. This looked like a generator hallucination that slipped past verification, but wasn't: `data/schemes/PM-KISAN.csv` itself contained "Rs.60001" and "Rs.20001" in two rows sourced from `RevisedFAQ.pdf` (the same PDF `pypdf` had flagged with an `incorrect startxref pointer` warning back when `scripts/fetch_scheme_data.py` first downloaded it in Week 1 — a structurally malformed PDF, not a clean one). The generator correctly used what was in its context; the verifier correctly confirmed the claim against that same context; the dataset itself was wrong. Scope-checked with `grep`: isolated to exactly those 2 of 43 PM-KISAN rows, no other scheme file affected.
**Fix:** Corrected both rows directly in `data/schemes/PM-KISAN.csv` (`Rs.60001` → `Rs.6000/-`, `Rs.20001` → `Rs.2000/-`), matching the correct figures already present in 3 other PM-KISAN rows sourced from the Operational Guidelines PDF. Rebuilt the index and re-ran the same demo question to confirm the fix. This is a hand-patch of a generated file, not a code fix — `scripts/fetch_scheme_data.py`'s `RevisedFAQ.pdf` source will reproduce the same corruption if re-run, since the root cause is `pypdf`'s extraction of specific glyphs in that one malformed PDF, not a general parsing bug with an obvious regex fix (unlike P-002's "Rs." sentence-boundary issue). Documented here so a future re-fetch knows to re-check this specific pattern rather than trusting the output blindly.
**Lesson:** A "SUPPORTED, high confidence" verdict only means the claim matches its evidence — it says nothing about whether the evidence itself is correct, and this project's whole knowledge base is scraped, not authored, so that assumption needed to actually be checked somewhere. It happened to surface by chance during ad hoc demo testing rather than through the 60-question evaluation set, which suggests the eval set may have other undetected source-data errors nobody has gone looking for. Given remaining time, spot-checking a sample of `data/schemes/*.csv` rows against their real source documents would be a reasonable use of it — this wasn't done here, only the one bug that happened to surface live.

### P-008: Re-ran verification against the corrected data with evidence-text logging — diagnosed the "12 unexplained" cases, found run-to-run non-determinism
**Week:** 4
**Problem:** P-006's second correction left 12 false positives (claims that were complete, accurate, and correctly-scoped, yet still flagged) as genuinely unexplained — `verifier_results.csv` only logged the top evidence *source*, not the full evidence *text* sent to `judge()`, so there was no way to tell whether the judge saw the right passage and misjudged it, or saw a subtly wrong one. Fixed the logging gap (`evidence_sources`, `evidence_text` columns added to `scripts/verify_answers.py`), rebuilt the index against the post-P-007 corrected `PM-KISAN.csv` (three attempts failed on the same low-memory condition as before — see P-005 — succeeded on the fourth once free RAM reached ~6GB), and re-ran verification on all 212 claims fresh.
**Fix:** Not a fix — a diagnosis. Reading the actual evidence text for the previously-unexplained cases found two distinct, concrete mechanisms, not one:

1. **Retrieval losing to inconsistent fact granularity.** Several `data/schemes/*.csv` rows are one clean sentence; others (e.g. Post-Matric Scholarship's "V. Value of Scholarship" row) are massive multi-paragraph blocks covering a dozen unrelated sub-topics — book banks, CPL courses, disability allowances, and the Group I-IV maintenance-allowance table, all in one row. A query about one specific sub-fact (e.g. "Group I ke liye 1200 rupees per month hostellers") competes against that entire diluted block's embedding, and often loses to a short, topically-adjacent-but-actually-wrong fact instead — confirmed directly: the claim above retrieved Post-Matric Scholarship's separate *Maharashtra-specific* rate range (₹250-700, ₹400-1350/month) both times this was tested, never the national Group I-IV table the claim was actually about, even though that table exists in the dataset. ADR-011's assumption that "facts are already short enough to embed directly, no chunking needed" holds for most rows but breaks down for these oversized ones — a genuine, previously undiagnosed retrieval-quality issue, distinct from wrong-scheme retrieval (P-004) and absence-claim mishandling (P-006).
2. **Genuine LLM-judge misjudgment on complete, correct evidence.** Q42's "Agar aap SC category se hain toh aapko caste certificate ki copy bhi lagani hogi" retrieved the *entire* correct "Procedure for Applying" passage, including item (d), the exact sentence requiring a caste certificate — and still came back CONTRADICTED (0.86-0.92 confidence across both runs). Nothing to blame on retrieval, decomposition, or scheme-matching here: the judge had the right answer in front of it and got it wrong anyway. This is a real reliability ceiling on the LLM-as-judge approach (ADR-001) that no amount of retrieval or decomposition tuning would fix.

A third finding, incidental to the above but worth flagging on its own: **re-running verification is not deterministic**, despite `temperature=0`. Comparing this run against the prior one on the exact same 212 claim texts (only 2 of 172 facts' text changed, from the P-007 fix): 3 individual claims flipped verdict on true-hallucinated claims alone (2 newly missed, 1 newly caught), net recall moved from 0.75 to 0.71, and total false positives moved from 66 to 65 (partly explained by Q9's fix, partly by this same instability). Headline numbers from any single run should be read as one sample, not an exact, reproducible measurement.
**Lesson:** "Unexplained" is a diagnosis gap, not a dead end — the fix wasn't in the verifier or the decomposition, it was in the *logging*, which had been throwing away the one piece of information (the actual evidence text) needed to tell these failure modes apart. Build in the ability to inspect what a component actually saw before concluding a failure has no cause. Separately: any reported precision/recall number for an LLM-judge-based system should be understood as a point estimate with real run-to-run variance, not a fixed ground truth about the system's performance — a single re-run moving recall by 4 points on identical input is a meaningful amount of noise for a 212-claim evaluation set this size.

### ADR-015: Implemented the three legitimately fixable P-008 causes; deliberately left two undone
**Decision:** Of P-008's five diagnosed causes of low precision, three got actual code/data fixes and two were left alone on purpose:
1. **Decomposition fragment filter** (`src/decomposition.py`) — `decompose()` now drops any claim under `MIN_CLAIM_WORDS=3` words after splitting, removing degenerate fragments like `"EWS"` and `"Assam, Meghalaya"` before they reach verification. Threshold chosen conservatively: checked against real bad fragments (dropped) and real short-but-legitimate claims like `"Bank account details"` (3 words, kept) before picking it, specifically to avoid trading false positives for false negatives on short real claims.
2. **Verifier prompt fix for absence-claims** (`src/verification.py`'s `VERDICT_PROMPT`) — added explicit instructions for claims that are themselves statements about what the evidence does or doesn't say: judge whether the topic genuinely appears in the evidence, don't default to UNVERIFIABLE. Tested directly against the two known failure directions before rollout — a true "no info" claim flipped UNVERIFIABLE→SUPPORTED, a false "no info" claim flipped SUPPORTED→CONTRADICTED, both as intended.
3. **Data granularity fix** (`scripts/split_oversized_row.py`, one-off) — split Post-Matric Scholarship's 11,268-character "V. Value of Scholarship" row (the confirmed culprit behind the Group I-IV maintenance-allowance retrieval misses) into 12 atomic facts. Not integrated into `scripts/fetch_scheme_data.py`'s live-fetch heuristics — this was a manual, one-off correction of the worst offender, not a general parser fix; other still-large rows (e.g. Post-Matric's "III. Conditions of Eligibility" at 4,368 chars) were left as-is, out of scope for this pass.

**Left deliberately unfixed**, per explicit user decision when presented with the choice:
- **Scheme-filtered retrieval** — not wired into the core pipeline, since a real user's question doesn't arrive pre-labeled with which scheme it's about; filtering retrieval by the known-correct scheme would improve eval numbers without being representative of real deployment.
- **The genuine LLM-judge misjudgment case** (Q42, correct evidence, wrong verdict anyway) — not prompt-engineered around. This is treated as a disclosed limitation of the LLM-as-judge method, not a bug with a fix.

**Why:** Fix what's a real, general defect (decomposition producing non-claims, a prompt gap, a known-bad data row) without disguising the pipeline's real capability by cheating on evaluation-only signal (scheme labels) or pretending an LLM reasoning failure can be reliably prompted away.
**Impact:** Required a full index rebuild (data changed) and full re-verification run (retrieval and prompt both changed) to get before/after numbers — see the entry immediately following this one for results. `MIN_CLAIM_WORDS=3` is a blunt instrument: it does not catch every damaged fragment (e.g. a 4+ word claim that lost its antecedent across an "aur" split, like Q38's original "day scholars" figures — though those specific ones are now moot since the underlying data row was also fixed).

### ADR-016: Multi-key failover for Groq API calls
**Decision:** `config/settings.py` now reads `GROQ_API_KEY_2`, `_3`, `_4` (optional, alongside the required `GROQ_API_KEY`) into `GROQ_API_KEYS`. `src/generation.py` exposes `get_clients()` (one `Groq` client per configured key). `judge()` in `src/verification.py` tries every configured client in sequence on a `RateLimitError` before sleeping with exponential backoff, remembering which key last succeeded (`_last_good_client`) so subsequent calls don't re-try an exhausted key first.
**Why:** Re-verifying all 209 claims after ADR-015's fixes repeatedly hit Groq's 200k-tokens/day quota with a single key, recovering only a couple of claims' worth every few minutes near the ceiling — a single key wasn't enough to finish a same-day re-run. The user has multiple Groq accounts; using their keys as failover was their explicit choice after being told this may be against some platforms' terms of service for circumventing a per-account free-tier limit (not confirmed either way for Groq specifically).
**Impact:** Fully backward compatible — with one key configured, behavior is identical to before (single client, exponential backoff on rate limit). `get_client()` still works for any caller that only needs one client. No change to `src/generation.py`'s `generate_answer()` — it still only uses the first key, since generation wasn't the bottleneck being solved here.
